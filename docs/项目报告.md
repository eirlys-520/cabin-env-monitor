# 基于 IMX6ULL 的密闭舱体多参数监测与分级告警系统

## 项目报告

---

## 摘要

本项目面向储能设备舱、小型电气设备隔间等密闭舱体的现场安全监测需求，以 IMX6ULL（Cortex-A7，Linux）为核心构建一台本地自治的边缘监测网关。系统通过 RS485、SPI、I2C、单总线、ADC、GPIO 六类硬件接口接入温湿度、振动、三轴姿态、光照、烟雾、火焰共七类传感器，采用"多线程并行采集 + 线程邮箱（消息队列）+ 互斥锁保护共享资源"的软件架构，在设备本地完成多源信号融合研判、三级风险仲裁、分级声光告警、LCD 现场显示与 SQLite 数据存储，网络仅作为日志上传的辅助通道。

系统设计的核心取舍是：**所有安全决策在本地闭环完成，云端不参与控制**。网络断开时，采集、研判、告警、存储、显示全部正常工作，不因网络异常丧失现场告警能力。项目重心放在底层外设驱动、可靠通信时序、实时任务调度与多源融合逻辑上，而非云端平台开发。

**关键词**：IMX6ULL；嵌入式 Linux；多传感器融合；线程邮箱；互斥锁；本地自治；分级告警

## 第一章 项目概述

### 1.1 项目背景

储能设备舱、配电设备舱、小型电气设备隔间这类密闭舱体具有三个典型特征：电气元器件集中、空间完全封闭、长期无人值守。这类场景下四类隐患具有高度现实性：

- **高温高湿**：密闭环境散热条件差，湿热环境加速线路绝缘老化；
- **起火燃烧**：电池热失控、接触不良打火后可燃气体积聚并发展为明火；
- **外力破坏**：搬运撞击、人为破坏导致舱体结构受损；
- **姿态异常**：地基沉降、搬运倾斜导致舱体倾倒，引发内部设备位移短路。

这些隐患的共同点是**发生在封闭空间内部，且物理量本身不具备可见性**。烟雾浓度、可燃气体浓度需要接触式气敏元件测量，倾角需要重力加速度投影计算，振动需要加速度计量化，这些都无法通过"看"获得。

市面商用密闭空间监测成套设备存在三个问题：

| 问题 | 具体表现 | 本项目改进 |
| --- | --- | --- |
| 闭源封闭 | 采购后无法修改阈值逻辑、无法新增测点，二次开发困难 | 全部代码自主实现，阈值与研判规则可配置 |
| 成本高 | 成套设备价格高，小规模部署不经济 | 采用通用传感器模组 + 通用开发板，成本可控 |
| 依赖云端 | 部分设备丧失网络后即丧失告警能力 | 本地闭环决策，网络仅用于日志上传 |

### 1.2 场景不可替代性论证

针对"这类监测能否被摄像头方案替代"的质疑，从物理层给出四点论证，这是本项目立论的基础：

**（1）密闭舱体内部无成像条件。** 舱体运行时完全封闭，无外部光源。依赖环境光的视觉方案在无光条件下无法成像；主动补光方案在长期功耗与布线成本上不成立，且红外补光只能成像表面轮廓，无法反映任何内部状态量。

**（2）关键参量不具备视觉可测性。** 可燃气体浓度、湿度、撞击加速度、静态倾角均属于**非光学物理量**，不存在可供 CCD/CMOS 感光的光学表征。这类量的测量必须依赖敏感元件与被测对象的物理接触（气敏材料吸附、质量块惯性形变、热敏/湿敏材料特性变化）。

**（3）即使失效，响应路径也完全不同。** 摄像头方案的输出是"图像"，还需要额外的图像理解才能得到"有烟/有火"的结论，链路长、延迟高且需大量算力（IMX6ULL 单核 A7 无法承担）。本项目采用敏感元件直接输出标量/模拟量，主控只需阈值比较与融合，响应路径短、确定性强。

**（4）早期隐患先于视觉表征出现。** 燃烧早期的可燃气体挥发（MQ-2 可感知）、EMI 导致的异常抖动（ADXL345 可感知）均早于可见烟雾与形变。等到视觉可识别时，事故往往已经不可逆。

因此本项目的真正价值不在于"看清某样东西"，而在于**"量化不可见的物理量，并据此做出确定性的本地控制决策"**——这正是嵌入式系统的不可替代之处。

### 1.3 项目目标

1. 完成六类硬件接口（RS485/SPI/I2C/单总线/ADC/GPIO）在 Linux 下的外设驱动与应用层通信；
2. 构建多线程 + 线程邮箱的软件架构，实现采集、研判、输出、存储、上传五类任务的解耦；
3. 实现多信号融合的风险研判算法，输出三级风险等级，并支持优先级仲裁与防抖复位；
4. 实现本地自治：断网后全部核心功能不受影响，联网后历史数据可补传；
5. 提供 LCD 本地人机界面与 SQLite 本地数据留存；
6. 通过 MQTT 将环境与告警日志上传至云端，供远端存档与后续扩展。

### 1.4 边界说明

为明确范围，本项目**不包含**以下内容：不做灭火/排风等执行机构联动控制（预留接口）；不做图像采集与视觉识别；云端不做任何控制决策，仅接收日志；不做手机 App，远端查看扩展为后续工作。

## 第二章 需求分析

### 2.1 监测对象与感知手段对照

| 风险类型 | 物理表征 | 感知手段 | 硬件接口 | 摄像头能否替代 |
| --- | --- | --- | --- | --- |
| 高温高湿老化 | 温度、相对湿度上升 | DHT11 温湿度 | 单总线 | 否，无形无色的环境变量 |
| 可燃气体/烟雾 | 还原性气体浓度、气溶胶 | MQ-2 气敏元件 | ADC 通道 1 | 否，气体无视觉表征 |
| 明火 | 特定波长红外辐射 | 火焰传感器 | ADC 通道 2 | 舱内无光且火焰不可见光路 |
| 撞击/异常抖动 | 结构振动加速度 | 振动变送器 | RS485（Modbus RTU） | 否，振动不可见且需接触式安装 |
| 倾斜/倾倒 | 重力在三轴的分量 | ADXL345 三轴加速度 | SPI | 否，静态倾角无法视觉测量 |
| 外壳破损 | 舱内光照突变 | BH1750 光照 | I2C | 否，舱内无光环境视觉无法成像 |

### 2.2 功能需求

**（1）环境与风险参数采集**

- 采集舱内温度、湿度，周期 2 s；
- 采集舱内光照强度，作为外壳破损辅助判据，周期 1 s；
- 经 RS485（Modbus RTU）轮询振动变送器，获取量化振动幅值，周期 200 ms；
- 经 SPI 读取 ADXL345 三轴原始数据，计算倾角，采样率 100 Hz；
- 经 ADC 同步采集烟雾、火焰两路模拟量，采样率 10 Hz。

**（2）多源融合研判**

- 支持单信号触发判定；
- 支持多信号组合条件判定（如"烟雾 + 火焰"双鉴、"倾角 + 振动"互证）；
- 输出三级风险等级，并给出本次判定的触发条件文本。

**（3）分级声光告警**

- 一级（提示）：仅指示灯，蜂鸣器不响；
- 二级（隐患）：指示灯闪烁 + 蜂鸣器间歇鸣响；
- 三级（高危）：指示灯爆闪 + 蜂鸣器持续高频鸣响。

**（4）本地可视化**

- LCD 实时展示七类感知参数、当前风险等级、最近告警记录、传感器在线状态、网络状态。

**（5）本地数据存储**

- SQLite3 保存环境日志与全部告警事件，支持告警记录的条件查询与历史翻阅。

**（6）数据上云**

- MQTT 上传环境参数与告警事件，云端仅存档，不参与本地控制。

**（7）故障自诊断**

- 传感器连续多次读取无应答时，判定离线并产生故障提示，LCD 标记离线设备，事件入库并上传。

### 2.3 非功能需求

| 类别 | 指标 |
| --- | --- |
| 离线自治 | 断网后采集、研判、告警、存储、显示全部正常；联网后自动补传断网期间告警记录 |
| 实时性 | 火焰类紧急事件从 ADC 采样到蜂鸣器响 ≤ 1 s；普通环境变量刷新周期 ≤ 2 s |
| 并发安全 | 多路事件同时上报时，风险判定串行执行，状态不混乱、消息不丢失 |
| 稳定性 | 单次数值跳变不触发告警；所有阈值具备回差（迟滞），消除临界抖动 |
| 可扩展性 | 阈值、使能开关、组合规则均可配置，新增测点只需增加一个采集线程与一条消息类型 |
| 资源占用 | 整机内存占用 ≤ 40 MB，适配 IMX6ULL 算力与存储资源 |

### 2.4 关键难点

1. **DHT11 单总线时序在 Linux 用户态的实现**：起始信号与数据位判定精度在微秒级，而 Linux 为分时系统，需要结合高精度定时器、忙等待与线程优先级策略才能保证解码正确；
2. **Modbus RTU 主站时序与 CRC 处理**：RS485 半双工方向切换需要精确控制收发使能延迟，避免丢帧与帧尾截断；
3. **多路并发事件的融合逻辑一致性**：必须保证任意时刻只有一条消息改写共享风险状态，同时不能因为加锁导致消息队列积压溢出。

## 第三章 系统总体方案

### 3.1 设计原则

1. **本地闭环优先**：所有影响安全的决策在设备本地完成，网络只是日志外送通道；
2. **分层解耦**：采集、仲裁、输出三层严格分离，采集线程不直接操作告警外设；
3. **消息驱动**：线程之间不共享业务数据全局变量，全部通过线程邮箱传递结构化消息；
4. **单点受控共享访问**：风险状态作为共享资源统一由调度线程在互斥锁保护下修改；
5. **故障导向安全（fail-safe）**：传感器失效、线程异常均以"告警 + 标记"方式呈现，绝不静默失败；
6. **可配置**：所有阈值参数外置数据库，支持热更新，避免频繁重新编译。

### 3.2 总体架构

系统分为四层：

```
+-------------- 感知层：六类硬件接口 / 七类传感器 ----------------+
|  RS485振动变送器 | SPI ADXL345 | I2C BH1750 | 单总线 DHT11      |
|  ADC烟雾 MQ-2    | ADC火焰     | GPIO 中断输入 / 输出            |
+-----------------------------|-----------------------------------+
                              v   Linux 字符设备 / IIO 子系统
+-------------- 驱动与中间件层 ------------------------------------+
|  自写 Modbus RTU 主站 | spidev | i2c-dev | gpio时序 | IIO ADC    |
|  统一转换为本地消息，送入线程邮箱                                |
+-----------------------------|-----------------------------------+
                              v  结构化消息 mailbox
+---- 核心仲裁层（IMX6ULL 本地闭环，断网照常运行）----------------+
|  业务调度线程：融合研判 -> 风险分级 -> 优先级仲裁 -> 防抖复位    |
|  互斥锁共享资源：当前风险等级 / 触发条件表 / 风险计时器          |
+---|-------------|-------------|------------|--------------------+
    v             v             v            v
+---------+   +----------+   +----------+   +----------+
| 告警    |   | LCD      |   | SQLite   |   | MQTT     |
| 输出    |   | 刷新     |   | 存储     |   | 上传     |
+---------+   +----------+   +----------+   +----|-----+
                                                  v 仅上传，不参与控制
                                        +------------------------+
                                        | 云服务器  MQTT Broker  |
                                        +------------------------+
```

## 第四章 硬件选型与设计

### 4.1 主控选型

选用 IMX6ULL（Cortex-A7，主频 528 MHz~800 MHz）Linux 开发板，理由：

- 同时具备 UART、SPI、I2C、ADC、GPIO、LCD 控制器，本项目需要的六类接口全部片上提供，不需要额外扩展；
- 运行完整 Linux，可直接利用字符设备、IIO 子系统、pthread 多线程等机制，工程结构规范；
- 相比 STM32 方案可承载更多并发线程与 SQLite 存储；相比树莓派等方案在工业现场环境适应性与国产化平台上更贴合；
- 算力不足以也**不适合**承担视觉算法，恰好把项目重心约束在底层驱动与逻辑确定的研判上。

### 4.2 感知单元选型

| 接口类型 | 模块 | 作用 | 选型理由与技术要点 | 对比备选方案 |
| --- | --- | --- | --- | --- |
| RS485（Modbus RTU） | 振动传感器（变送器） | 识别撞击、设备异常振动 | 差分传输抗电磁干扰，适合舱内线缆复杂环境；标准 Modbus RTU 协议直接输出量化幅值，主控无需复杂信号标定；总线形式便于扩展多个测点 | 数字量振动开关：只有阈值跳变，无法量化；SPI 加速度做原始振动：需自行积分且成本高 |
| SPI | ADXL345 三轴加速度 | 舱体倾斜/倾倒姿态、冲击识别 | SPI 速率高，姿态刷新快；直接输出三轴原始加速度，既可静态倾角也可动态冲击；与 RS485 振动变送器互补 | MPU6050：带陀螺但需姿态解算幅度更大；倾角开关：单点阈值、不可量化 |
| I2C | BH1750 光照强度 | 外壳破损辅助判断 | I2C 数字输出免标定；密闭舱正常内部光照微弱，破损时数值显著上升 | 光敏电阻 + ADC：一致性差、需分压标定；SPI 光照：无必要占用 SPI |
| 单总线 | DHT11 温湿度 | 高温高湿老化判据 | 单根信号线，布线简单；用于验证 Linux 下单总线时序驱动开发攻关；精度满足分级预警需求 | SHT30（I2C）：精度更高但失去单总线时序的工程训练价值；NTC 热敏 + ADC：需标定曲线 |
| ADC 通道 1 | MQ-2 烟雾/可燃气体 | 火灾早期隐患识别 | 模拟量连续输出，可设多级浓度阈值；与火焰构成双鉴 | MQ-2 数字量模块：只有开关量，无法分级 |
| ADC 通道 2 | 火焰传感器 | 明火高危判定 | 对特定红外谱段敏感；取模拟量而非 DO 开关量，可设置置信分级 | 数字输出型：易受干扰误触发，且无法感知强度 |
| GPIO | 状态指示灯 ×3、有源蜂鸣器 | 分级声光告警 | 驱动简单、可靠；有源蜂鸣器只需电平驱动，不需 PWM 调音 | 无源蜂鸣器：需 PWM 驱动，复杂度上升 |
| 显示 | RGB LCD（800×480） | 本地人机交互 | Framebuffer 直写，断网可显示；现场无上位机时的唯一查看手段 | 串口屏：需另购、协议受限，且失去 Framebuffer 底层实践 |
| 存储 | eMMC / SD + SQLite3 | 本地持久化 | 无独立后台进程，资源占用低；结构化存储支持条件查询 | 文本日志：检索困难；MySQL：资源占用过大 |
| 通信 | 以太网 + MQTT | 日志上传 | 轻量发布-订阅，内置断线重连；决策在本地，弱网络依赖 | HTTP 轮询：开销大；私有 TCP：无生态工具 |

### 4.3 硬件设计要点

- **RS485 总线**：末端并 120 Ω 终端电阻，总线采用手拉手拓扑；收发器优选带自动收发方向控制的型号，避免软件方向切换导致的帧尾截断；
- **ADC 参考**：IMX6ULL ADC 参考电压为 3.3 V，MQ-2 与火焰模块输出需保证 0~3.3 V 范围内；对每一路做滑动窗口均值滤波，抑制电源纹波；
- **GPIO 隔离**：指示灯与蜂鸣器经三极管/MOS 驱动，不直接由 IO 灌流；若后续接入 220 V 执行机构，须经光耦隔离 + 继电器；
- **电源设计**：建议双路供电，弱电侧（主控与传感器）与后续执行机构强电侧分离，避免电机启停干扰 ADC 采样；
- **安装布局**：ADXL345 需刚性固定于舱体主承力面；MQ-2 建议安装在舱内顶部（可燃气体上浮）；火焰传感器需对准易起火区域且避开直射光源。

## 第五章 软件架构设计

### 5.1 线程划分

系统共 11 个线程，按职责分为采集、仲裁、输出三类：

| 线程 | 类别 | 周期 | 职责 | 输出消息 |
| --- | --- | --- | --- | --- |
| geomag（振动）RS485 采集线程 | 采集 | 200 ms | Modbus RTU 轮询振动变送器，组帧/解帧/CRC 校验 | MSG_SENSOR_VIB |
| SPI 姿态采集线程 | 采集 | 10 ms | 读取 ADXL345 三轴数据，滑动滤波后计算倾角 | MSG_SENSOR_POSE |
| BH1750 采集线程 | 采集 | 1 s | I2C 读取光照强度，与基线比较 | MSG_SENSOR_LIGHT |
| DHT11 采集线程 | 采集 | 2 s | 单总线时序读取温湿度 | MSG_SENSOR_ENV |
| ADC 采集线程 | 采集 | 100 ms | IIO 读取两路 ADC，换算烟雾/火焰强度 | MSG_SENSOR_FIRE |
| **业务调度线程** | 仲裁 | 事件驱动 | 接收全部感知消息，融合研判、风险分级、优先级仲裁、复位判定 | MSG_ALARM_SET / MSG_ALARM_RESET / MSG_UI_REFRESH / MSG_DB_WRITE / MSG_MQTT_UP |
| 告警输出线程 | 输出 | 事件驱动 | 驱动指示灯与蜂鸣器，按等级执行节奏表 | — |
| LCD 刷新线程 | 输出 | 500 ms / 事件 | Framebuffer 绘制参数、等级、告警列表 | — |
| SQLite 存储线程 | 输出 | 事件驱动 | 统一处理数据库读写，避免业务线程被 IO 阻塞 | — |
| MQTT 上传线程 | 输出 | 事件驱动 + 心跳 | 环境上报、告警上报、离线补传 | — |
| 看门狗/自检线程 | 输出 | 5 s | 检测各线程存活与设备在线状态，喂硬件看门狗 | MSG_SENSOR_OFFLINE |

> **设计约束**：采集线程**不得**直接操作指示灯、蜂鸣器、LCD、数据库与网络，必须经业务调度线程仲裁后由对应输出线程执行。采集线程也不得修改共享风险状态。

### 5.2 线程邮箱设计

**（1）消息结构**

```c
typedef struct {
    unsigned int  type;        /* 消息类型 */
    unsigned char src;         /* 来源线程 ID */
    unsigned char prio;        /* 优先级 0最高 */
    unsigned int  seq;         /* 投递序号，用于排查丢消息 */
    struct timespec ts;        /* 产生时间戳 */
    union {
        float    f_val[4];     /* 通用数值负载 */
        int      i_val[4];
        char     text[64];     /* 触发条件文本 */
    } payload;
} mailbox_msg_t;
```

**（2）消息类型表**

| 消息类型 | 发送方 | 接收方 | 说明 |
| --- | --- | --- | --- |
| MSG_SENSOR_ENV | DHT11 线程 | 调度线程 | 温度、湿度刷新 |
| MSG_SENSOR_LIGHT | BH1750 线程 | 调度线程 | 光照强度刷新 |
| MSG_SENSOR_VIB | RS485 线程 | 调度线程 | 振动幅值刷新 |
| MSG_SENSOR_POSE | SPI 线程 | 调度线程 | 三轴倾角刷新 |
| MSG_SENSOR_FIRE | ADC 线程 | 调度线程 | 烟雾、火焰数值刷新 |
| MSG_SENSOR_OFFLINE | 自检线程 | 调度线程 | 某传感器离线/恢复 |
| MSG_ALARM_SET | 调度线程 | 告警线程 / UI / DB / MQTT | 设定风险等级（含等级与触发条件） |
| MSG_ALARM_RESET | 调度线程 | 告警线程 / UI / DB / MQTT | 风险解除复位 |
| MSG_DB_WRITE | 调度线程 | 存储线程 | 环境日志/事件落库 |
| MSG_UI_REFRESH | 调度线程 | UI 线程 | 界面刷新 |
| MSG_MQTT_UP | 调度线程 | MQTT 线程 | 上报环境/告警 |
| MSG_CFG_UPDATE | MQTT 线程 | 调度线程 | 远程更新阈值配置 |
| MSG_HEARTBEAT | 各线程 | 自检线程 | 线程存活心跳 |

**（3）投递原则**

- **变化上报**：数值越限或发生显著变化时才投递，避免等量消息刷屏；
- **周期兜底**：环境变量即使无变化，也按 10 s 周期投递一次，供 UI 与 (re) 云端保活使用；
- **非阻塞**：队列满时丢弃低优先级的周期性消息并计数，**永不丢弃告警类消息**；
- **优先级队列**：MSG_SENSOR_FIRE 与 MSG_ALARM_SET 走高优先级队列，确保端到端时延最短。

### 5.3 互斥锁与共享资源

| 共享资源 | 保护方式 | 访问者 |
| --- | --- | --- |
| 当前风险等级 | pthread_mutex_t g_risk_lock | 仅调度线程写；UI/告警/MQTT 只读快照 |
| 触发条件表（哪些条件正在成立） | 同上锁 | 仅调度线程写 |
| 风险持续/复位计时器 | 同上锁 | 仅调度线程写 |
| SQLite 连接句柄 | SQLite 线程独占 + busy_timeout | 仅存储线程 |
| 消息队列 | 内部 mutex + cond | 全部线程 |

**关键约束**：一次融合研判过程必须在持锁状态下一次性完成"读取多源输入 → 遍历规则表 → 计算新等级 → 更新条件表 → 更新计时器"，处理完毕释放锁后再处理下一条消息，保证任意时刻风险状态是完整一致的版本。

### 5.4 关键时序

- **火焰告警端到端时延**：ADC 采样（100 ms） → 越限判定 → MSG_SENSOR_FIRE → 调度线程唤醒（μs 级） → MSG_ALARM_SET → 蜂鸣器响。全流程实测目标 ≤ 1 s；
- **RS485 轮询**：单帧请求+应答按 9600 bps 计约 20 ms，预留 50 ms 超时，单轮控制在 200 ms 内完成；
- **DHT11 读取**：单总线约 4 ms 传输窗口，期间需短暂关闭调度抢占（提高线程优先级 + 忙等待），并在结束后立即恢复，避免影响其他线程实时性。

## 第六章 核心业务逻辑

### 6.1 数据预处理

所有原始数据在进入研判之前完成三级预处理，这是"鲁棒性"的来源：

1. **剔除野值**：与上一次有效值偏差超过物理上限（如温度跳变 > 10 ℃/s）的样本直接丢弃并计数；
2. **滑动平滑**：窗口 5 点均值滤波，抑制电源纹波与瞬时干扰；
3. **持续时间确认（防抖）**：越限必须连续保持 N 次采样才算成立。火焰 N=1（要快），烟雾 N=3，振动 N=5，倾角 N=5，温湿度 N=3，光照 N=5。

### 6.2 研判规则表

| 编号 | 触发条件 | 风险等级 | 说明 |
| --- | --- | --- | --- |
| R1 | 温度 > 55 ℃ 或 湿度 > 80 %RH | L1 提示 | 阈值可配置 |
| R2 | 光照 > 基线 + 150 lx 并持续 | L1 提示 | 疑似外壳破损，需结合 R6 |
| R3 | 烟雾 ADC ≥ 预警阈值 | L2 隐患 | 单一判据 |
| R4 | 振动幅值 ≥ 阈值并持续 3 s | L2 隐患 | 疑似撞击/设备异常 |
| R5 | 火焰 ADC ≥ 阈值 | L3 高危 | 立即升级 |
| R6 | 倾角 ≥ 35° | L3 高危 | 倾倒 |
| R7 | R3 且 R5 同时成立 | L3 高危（高置信） | **火情双鉴**，消除单一元件误报 |
| R8 | R4 且 R6 同时成立 | L3 高危（高置信） | **姿态互证**，排除安装松动导致的误报 |

> 组合规则的价值：单一传感元件易受环境干扰（如火焰传感器受电焊弧光干扰），通过"另一种物理原理的信号同时成立"来交叉确认，是本项目融合研判的核心思路。

### 6.3 等级仲裁与复位

**（1）升级仲裁（取高不取低）**

多个条件同时成立时，最终等级 = 所有命中规则中的最高等级；同级多条同时成立则在告警记录中列出全部触发条件，便于事后复盘。

**（2）优先级覆盖顺序**

明火火情 > 舱体倾倒 > 烟雾隐患 > 舱体外壳破损 > 温湿度异常

高优先级事件可直接覆盖当前低等级状态，无需等待低等级复位。

**（3）复位规则（迟滞 + 延时）**

需同时满足两个条件才复位——① 全部触发条件回归到**带回差的正常区间**（如温度回落至 52 ℃ 以下，与 55 ℃ 触发阈值形成 3 ℃ 回差）；② 已持续保持 T=60 s（可配置）。这一设计消除阈值临界点反复抖动导致的告警闪烁。

**（4）复位动作**

熄灭对应指示灯 → 停蜂鸣器 → 记录告警结束时间 → 上传闭环事件。

### 6.4 多事件并发处理流程

1. 多个采集线程同时将异常事件封装消息投递至线程邮箱；
2. 业务调度线程按优先级依次取消息；
3. 取到消息后**加互斥锁**，完成一次完整等级判定；
4. 记录本次判定版本号，写入共享风险状态；
5. 释放锁，向告警输出线程、UI、存储、MQTT 投递结果消息；
6. 处理下一条消息。

结果：即使十余路消息在极短时间内涌入，风险状态也只会按"一次一个版本"的方式有序演进，不会出现状态半写或告警遗漏。

### 6.5 传感器离线与自恢复

- 连续 3 次读取失败/CRC 错误/超时 → 标记该设备离线（fail_cnt++）；
- fail_cnt ≥ 3 → 投递 MSG_SENSOR_OFFLINE，LCD 打叉标记、故障灯点亮、事件入库并上传；
- 离线期间保持 5 s 一次的试探性重连；连续 3 次成功 → 判定恢复，投递恢复事件，清除 LCD 标记；
- 离线期间该路传感器**不参与**当前风险的"降级复位"计算，避免因设备掉线造成" 조건 消失"的错误复位。

> 最后一条是许多简单实现容易遗漏的坑：设备掉线≠条件回归正常，必须区别处理。

### 7.2 MQTT 协议设计

| 方向 | Topic | 载荷 |
| --- | --- | --- |
| 上行 | cabin/upload/env | 环境参数周期上报（10 s） |

| 上行 | cabin/upload/status | 设备在线状态与心跳（30 s） |

**告警上报载荷示例：**

```json
{
  "dev_id": "cabin-001",
  "event": "alarm",
  "level": 3,
  "rule": "R7",

  "cleared": 0,
  "seq": 10237
}
```

> `seq` 字段用于离线补传时的去重；QoS=1 保证至少一次送达；遗愿消息（Will）设置为离线状态，便于云端感知设备掉线。

## 第十一章 项目技术亮点

可以从嵌入式工程能力角度总结的十个点：

1. **六类硬件总线全栈落地**：RS485 Modbus RTU、SPI、I2C、单总线、ADC（IIO）、GPIO 中断/输出，覆盖嵌入式主流通信方式；
2. **自写 Modbus RTU 主站**：手工实现 CRC-16 校验、RTU 帧间隔判帧、超时重传，不依赖第三方库；
3. **Linux 用户态微秒级时序**：攻克分时系统下 DHT11 单总线位判定，结合高精度定时器、忙等待与 SCHED_FIFO 优先级；
4. **IIO 子系统多路 ADC 采样**：掌握 Linux 标准模拟量采集路径而非裸寄存器操作；
5. **多线程 + 线程邮箱架构**：线程间零业务全局变量，全部通过结构化消息通信，从根本上规避数据竞争；
6. **互斥锁保护共享研判资源**：保证多事件并发时风险状态一次一个完整版本地演进；
7. **多源融合与双鉴降误报**：不同物理原理的信号交叉验证，把"监测"提升为"研判"；
8. **迟滞与防抖工程化处理**：回差 + 持续时间确认，解决阈值临界抖动这一真实工程痛点；
9. **本地自治与故障导向安全**：断网可用、离线补传去重、设备离线不误判为条件回归；
10. **资源受限平台的精细控制**：SQLite WAL、队列丢弃策略、滑动窗口滤波、≤ 40 MB 内存占用，体现嵌入式资源意识。

## 第十二章 总结与展望

本项目围绕"密闭舱体内部不可见物理量的可靠测量"这一核心命题，构建了一台以 IMX6ULL 为核心的本地自治监测网关。与常见的"采集 + 上云 + 大屏"型物联网项目不同，本项目的价值重心放在了底层：六种总线的驱动能力、微秒级时序的攻克、环形通信的可靠性处理、实时任务调度架构、并发安全，以及把七个传感器的原始读数转化为可信风险结论的融合研判逻辑。这些能力不会随着视觉算法的进步而贬值，因为被测量的对象从根本上就不具备视觉表征。

**后续可扩展方向：**

- 增加 GPIO 继电器输出，接入排风机、断电闭锁装置，把"监测"升级为"监测 + 联动控制"闭环，届时互斥锁的价值将从"保护状态"升级为"保护执行机构"，工程深度进一步提升；
- 增加备用电源与超级电容，实现掉电后的最后时刻告警报送；
- 增加 LoRa 组网，形成多舱体分布式集中监测；
- 在 ADXL345 上扩展 FFT，实现轴承类转动设备的简易频谱健康诊断；
- 开发轻量 Web/小程序查询端，用于远程查看历史曲线与告警记录。
